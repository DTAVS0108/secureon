# Key rotation

Which secrets exist, where they live, and how to rotate each without breaking sign-in. Which are created on the first start and which you can supply: [Deployment § Secrets](../deployment.md#a2--secrets-created-on-the-first-start).

## OAuth / OIDC signing key (JWT)

Source: `SECUREONE_JWK_PRIVATE_KEY_PEM` when set, otherwise `platform_setting` key `oauth2_signing_jwk` (generated on the first start, private key encrypted with the encryption key). The JWKS `kid` of an env key is derived from its PEM.

Overlapping rotation (no token is rejected early):

1. Generate the new key: `openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out jwk-new.pem`.
2. Set **`SECUREONE_JWK_PRIVATE_KEY_PEM`** = new key and **`SECUREONE_JWK_PREVIOUS_PRIVATE_KEY_PEM`** = the old key's PEM (exactly as it was configured, so its `kid` stays the same).
3. Rolling restart. New tokens are signed with the new key only; `/oauth2/jwks` publishes **both** public keys, and the auth-server accepts tokens signed with either.
4. Wait at least the longest token lifetime that can still be in use (access token TTL; ID tokens are only checked at sign-in) plus resource-server JWKS cache time (typically ≤ 1 h).
5. Remove `SECUREONE_JWK_PREVIOUS_PRIVATE_KEY_PEM` and restart. Refresh tokens are opaque and unaffected.

A key SecureOne generated is rotated in the console (**Signing keys**), with the same overlap. To move from it to a key of your own: there is deliberately no private-key export. Either switch in a quiet window — tokens signed by the old key are rejected after the restart, users and apps simply sign in / refresh again — or, if you still have that key's PEM from when it was created, put it in `SECUREONE_JWK_PREVIOUS_PRIVATE_KEY_PEM`; the auth-server recognises it as the stored key and keeps publishing it under its original `kid`.

## SAML SP key (signing + decryption)

Source: `SECUREONE_SAML_SP_KEY_PEM` + `SECUREONE_SAML_SP_CERT_PEM`, otherwise `platform_setting` key `saml_sp_credential` (generated once on first SAML use, private key encrypted, self-signed certificate valid 10 years).

Every SAML IdP trusts this certificate (signed AuthnRequests / LogoutRequests, and the target of encrypted assertions), so rotation is coordinated with the IdP owners:

1. Generate: `openssl req -x509 -newkey rsa:2048 -nodes -days 3650 -subj "/CN=SecureOne SAML SP" -keyout saml-sp.key -out saml-sp.crt`.
2. Where the IdP supports two SP certificates (most enterprise IdPs do), add the new certificate there first.
3. Set the env vars, rolling restart. The SP metadata (`/api/v1/auth/federation/saml/{alias}/metadata`) now shows the new certificate.
4. Ask each IdP to re-import the SP metadata (or the new certificate), then remove the old certificate at the IdP.
5. IdPs that encrypt assertions must switch to the new certificate before step 3, or encrypted sign-ins fail until they do.

## IdP certificates (inbound SAML)

Providers configured with a **metadata URL** pick up the IdP's new signing certificate automatically (metadata is re-read every 10 minutes, and when the provider is saved). Providers configured manually need the new PEM pasted into **IdP signing certificate** before the IdP switches.

## Encryption key (`SECUREONE_ENCRYPTION_KEY`)

Encrypts stored secrets: SMTP/SMS credentials, IdP client secrets, MFA seeds, and the JWT / SAML private keys when generated by SecureOne.

- **First time (moving from the development fallback):** set it and restart. Values written earlier still decrypt with the database fallback key and are re-encrypted under the new key whenever they are saved again; re-save SMTP / SMS / federation settings and restart once to move everything over.
- **Replacing an existing key:** there is no automatic re-encryption from one environment key to another yet. Export the affected settings (SMTP/SMS passwords, IdP secrets), set the new key, restart, and enter the secrets again; generated JWT / SAML keys must then be supplied by env (or regenerated, which is a key rotation as above).
- Back the key up in your secret manager, **separately from database backups**.

## OTP pepper (`SECUREONE_OTP_PEPPER`)

Generated on the first start when not set, stored encrypted. Rotating invalidates unconsumed OTP hashes **and MFA recovery codes**: avoid it, and once you have set the variable, keep it.

1. Schedule maintenance window.
2. Update secret in vault/Kubernetes secret.
3. Rolling restart auth-server pods.
4. Users mid-OTP must request a new code.

## Database / Redis credentials

1. Rotate in PostgreSQL/Redis.
2. Update Kubernetes secret or env.
3. Rolling restart auth-server (sessions in Redis survive if URL unchanged).

## Session invalidation after compromise

```http
DELETE /api/v1/account/sessions
```

Platform operators can review `login_history` and revoke suspicious sessions per user via the sessions API when authenticated as that user, or flush Redis session namespace in emergencies (`secureone:session:*` — forces all users to re-login). Users who signed in through a SAML IdP are also signed out when the IdP sends a LogoutRequest (single logout).
